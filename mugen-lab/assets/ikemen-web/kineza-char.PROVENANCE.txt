SUPERSEDED BY kineza-char-v02.zip (RIG I23) -- AND THE DIAGNOSIS BELOW
WAS WRONG ON ONE KEY POINT.

The palette was NOT missing. All 768 bytes were present in every sprite;
only the single 0x0c delimiter byte that must precede them was absent --
23 bytes in a 2.1MB file. The text below concluding the palette "was
never written" and is "unrecoverable" is incorrect. It was reached by
checking for the delimiter, not finding it, and then running whole-file
byte accounting -- which cannot distinguish a palette inside a sprite's
own data block from image data, since those bytes are counted in the
block length. The trailing 768 bytes visibly decode as a real palette
(255 distinct colours, warm skin and hair tones); that was never checked.

I23 repairs it correctly by inserting only the delimiter and preserving
every original PCX and palette byte. Use kineza-char-v02.zip. The
silhouette pack described below was unnecessary; its [Size] retune, which
remains valid, was carried into v0.2.

kineza-char.zip — Kineza MUGEN prototype, repo-hosted character pack
====================================================================

Source: KINEZA_MUGEN_PROTOTYPE_V0_1.zip (DAI, 2026-09-18), described by
its own README as "a load-test and motion-test build, not the finished
fighter."

Layout changed from the original delivery: the folder was renamed from
Kineza_Prototype_V0_1/ to chars/kineza/ so the roster line is just
"kineza", matching the form of every other entry in the user's
select.def. Nothing inside the .def/.cns/.cmd/.air was edited.

kineza.sff IS NOT THE ORIGINAL FILE.
------------------------------------
The delivered SFF v1 had no palette. A PCX 8-bit image must end with a
0x0C marker byte followed by 768 bytes (256 RGB triplets); all 23
sprites were missing that block entirely, confirmed by full byte
accounting of the file (512-byte header + 2,163,794 bytes of sprite
blocks, zero gaps, zero unaccounted bytes). With no colour table the
8-bit indices are meaningless, and the character rendered on device as
magenta/green confetti.

The original palette is unrecoverable from the file: quantisation was
adaptive (all 256 indices in use, none above 0.5% of pixels), so each
index maps to a specific colour that exists nowhere in the delivery.

The SFF here has a STAND-IN silhouette palette attached by
tools' make_silhouette_sff.py: index 0 (75-84% of every sprite, already
the correct MUGEN transparent-background convention) stays background,
and indices 1-255 all take Kineza's canonical Prismatic Veil accent
colour 0x68ff8c from src/BattleConfig.js. The result is a flat green
silhouette.

THE COLOURS ARE FAKE. This does not fix the character. It exists so the
build can be used as what it says it is -- a motion test -- while the
SFF is regenerated upstream with its real palette attached. Everything
else in the file is untouched and was verified correct: RLE data decodes
to exactly 196,608 of 196,608 expected pixels on all 23 sprites, 512x384
dimensions, axis 256,340, subheader chain intact.

Upstream fix required: append 0x0C + the 768-byte palette to each
sprite's PCX data when writing the SFF. No other change is needed --
header, subheader chain, dimensions, axes, RLE, and the AIR/CNS/CMD
wiring were all correct as delivered and loaded with zero engine errors.


kineza.cns [Size] WAS RETUNED (2026-09-18)
------------------------------------------
The delivery set xscale/yscale = .5, which its own README flagged as
temporary and asked about directly ("Is the 0.5 scale correct beside the
existing roster?"). Measured answer: no.

Silhouette content is 329px head-to-feet, so at .5 he stood 164.5 units
tall. With no localcoord in the .def and mugenversion 04,14,2002, the
space is the 320x240 default -- a 240-unit-tall screen -- putting him at
68.5% of screen height. Kung Fu Man, MUGEN's own reference character,
sits at head.pos -90, about 37%. He was ~1.8x oversized.

Retuned to .3 -> 98.7 units, 41% of screen height: standard band, a
touch above KFM, which suits a lead character standing next to the
heavies in this roster. Every other [Size] value is expressed in game
units, so all of them were scaled by the same 0.6 ratio to keep collision
and reach consistent with the art:

  xscale/yscale    .5   -> .3
  ground.back      20   -> 12
  ground.front     18   -> 11
  air.back/front   16   -> 10
  height          170   -> 102
  attack.dist     160   -> 96
  proj.attack.dist 90   -> 54
  head.pos    -5,-155   -> -3,-99
  mid.pos      -5,-90   -> -3,-54

The .air needed no edit: Clsn boxes are in sprite-pixel space and MUGEN
scales them by xscale/yscale automatically.

Also measured and found CORRECT, contrary to an earlier guess: his feet
land 1-3px above the axis across all stance frames, so he plants on the
ground properly. The 44px of canvas below the axis is empty padding, not
a floating character.
